How the project uses models

In model-based development, we define the structure of the data, create models that follow that structure, and write transformations that work with those models. In our project, the model for a planned meal specifies its day, servings, and recipe. QVTo reads that information and creates a shopping-list model.

The four metamodels

Each box below names an Ecore class. Each arrow shows a reference from one class to another. A containment reference owns its children. A regular reference points to an existing object. 0..* means zero or more, 0..1 means optional, and 1 means exactly one.

Recipe book

RecipeBookowns 0..* →Recipe
RecipeBookowns 0..* →Ingredient
Recipeowns 0..* →RecipeIngredient
RecipeIngredientrefers to 1 →Ingredient

Ingredient stores the food’s name and category. RecipeIngredient stores the quantity and unit for a particular recipe. The Pasta entry belongs to the recipe book, and the recipe links to it through a row specifying 250 gr.

Read the QVTo transformation

QVTo is the operational part of QVT, which stands for Query/View/Transformation. We use it for a model-to-model transformation. In this project, a run reads an XMI model and creates another XMI model using rules written in NewTransformation.qvto.

Which models can the code work with?

transformation NewTransformation(
    in schedule : Schedule,
    out shopping : Shopping
);

in declares the input supplied when the code runs. out declares the output it creates. The modeltype declarations above this header identify the Ecore metamodels for Schedule, Shopping, and Recipes. Recipe data comes through the meal’s reference to the recipe book.

Where does it start?

schedule.rootObjects()[Schedule::MealSchedule]
    ->map toShoppingList();

main() selects the top-level MealSchedule and applies toShoppingList. A mapping is a named rule that takes a source object and creates a target object. This mapping copies week 5 and loops through each meal and its recipe ingredients.

How does it choose an aisle?

result.name := self.ingredient.category;
result.items += self.map toItem(
    mealServing, recipeServing);

Inside toAisle, self is the source recipe ingredient and result is the new aisle. The code takes the food’s category, such as Dry Goods, and adds the item created by toItem.

How does it calculate the amount?

result.name := self.ingredient.name;
result.unit := self.unit;
result.quantity :=
    self.quantity * mealServing / recipeServing;

toItem copies the food’s name and unit. For Pasta, 250 gr is the recipe amount for two servings. The schedule asks for three servings, so the result is 375 gr.

How the supermarket data could be used

From the project’s own values, the meal needs 375 gr of pasta, and the linked product comes in a 500 gr package priced at 15. If the group decides to buy whole packages, that requires one package and costs 15. The sample has a tomato ingredient but no tomato product, so these data alone only support a pasta price. Seeing the new input in the header tells you the file can be passed in. Reading the mappings and examining the output tells you whether package pricing works.

Decisions to make together

  • Review your teammate’s QVTo change and diagram. Run their version and inspect what it produces for Pasta and Tomato.
